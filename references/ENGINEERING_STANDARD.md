# 软件项目工程标准

版本 1.4 · 2026-11-03 · 适用于**所有**软件项目：从一次性脚本到长期运行的设备服务

这份文件是所有项目的**默认值**，不是法典：每条规则都写了为什么，强度按项目等级（第 0 节）缩放，任何一条都可以用一条 ADR 对某个项目关闭。它偏向谨慎而不是速度；小任务用判断力，但要把判断说出来。
项目根目录的 `ENGINEERING_STANDARD.md` 是它的副本；升级标准后重新复制。它由 `engineering-standard` skill 维护（`~/.claude/skills/engineering-standard/`）。
借鉴来源：Andrej Karpathy 的 LLM 编码四原则、Dietrich Gebert 的 ponytail、Jesse Vincent 的 superpowers、Matt Pocock 和 Addy Osmani 的 skills、Trail of Bits 的安全 skills、Claude Code 官方实践。取了什么、弃了什么、为什么，见 skill 的 `references/sources-review.md`；出处见附录 A。

# 第一部分 核心标准

## 0. 怎么用这份文件

1. 复制到项目根目录，命名 `ENGINEERING_STANDARD.md`。
2. 项目的 `CLAUDE.md` 第一行写 `@ENGINEERING_STANDARD.md`；`AGENTS.md` 做成指向 `CLAUDE.md` 的符号链接。这样 Claude Code、Codex、Cursor 等任何 AI 会话开工前读到的都是同一套规则。
3. 每条规则都写成能打勾的形式；审查（人或 AI）按第 13 节和第 30 节逐条对照，不凭感觉。
4. 规则和项目实际冲突时：改本文，并写一条 ADR 说明原因。不要默默违反。
5. 同一类错误第二次发生 ⇒ 不再写文档提醒，改为加一条会"变红"的自动检查（测试、lint 规则、CI 脚本）。
6. 本文分"核心"和"严格级"。核心是底线；严格级是默认开启的更高要求，可以用 ADR 对某个项目关闭单条。
7. **项目等级决定用多少流程。** 在 `quality-budget.toml` 的 `[project] tier` 里声明，审计脚本和审查都按它缩放：

| 等级 | 适用 | 必须 | 不要求 |
|---|---|---|---|
| 0 脚本 / 实验 | 一次性脚本、原型、< 300 行、不常驻 | git、README 一段、无密钥、`set -euo pipefail`、如实汇报 | CHANGELOG、ADR、docs/、质量预算、CI、独立审查；测试不强制，但有分支、循环、解析的逻辑建议写一个 |
| 1 工具 / 内部库 | 自己或团队用、不跑在设备上 | 核心 15 节；严格级的 15、16、21 | 18 资源预算、19 断电、24 分阶段发布、28 设备专项 |
| 2 产品 / 设备常驻 | 长期运行在设备或服务器上的服务（例如一台智能台灯的固件） | 全部核心 + 全部严格级 + 28 | — |
| 3 安全 / 运动 / 金钱 | 会动、会伤人或动钱的（例如导航机器人、支付） | 等级 2 全部 + 变异测试强制 + 两个独立审查 + 故障注入全部自动化 + 现场操作安全 | — |

   等级只能在 ADR 里降；升级随时可以。不确定选哪级，选高一级。
8. **小事用判断力，但要说出来。** 对一个 20 行的改动不写设计便签是对的，但变更说明里要写一句"S 级，跳过设计便签"。跳过没说，才是违规。

## 1. 原则（冲突时按这个顺序取舍）

1. **正确 > 可读 > 简单 > 快。** 性能只在测量过的热点上优化，测量数据写进提交说明。"最精简"不是目标：短而巧的代码是最难查的 bug 来源。
2. **机器能检查的，不靠人。** 格式、lint、测试、依赖审计、质量门槛全部自动化；审查不讨论这些。
3. **一个改动 = 代码 + 测试 + 文档（含 CHANGELOG），同一个提交。** 分开提交的文档一定会烂掉。
4. **不需要的不写（YAGNI）。** 模块按职责边界划分，不按"全面"。删掉它项目还能用，就不要加。问自己：资深工程师会不会说这过度设计了？会，就简化。
5. **15 分钟原则。** 任何新来的人或 AI，照 README 在 15 分钟内能跑起来、看懂日志、定位一个 bug。
6. **如实汇报。** 说清楚什么验证了、怎么验证的、什么没验证。模拟、本地、dry-run 通过 ≠ 真机通过。
7. **假设一切都会坏。** 断电、磁盘满、设备无响应、时间倒退、网络消失，都是正常工况，不是异常。
8. **规则服务于目标。** 流程量与规模和风险成比例（第 0 节的等级）；当某条规则让事情变差时，改规则（写 ADR），不要绕过它。
9. **最好的代码是没写的代码。** 写新代码前先走第 4 节的阶梯：真的需要吗 → 仓库里已有吗 → 标准库有吗 → 平台原生有吗 → 已装的依赖有吗 → 能一行吗 → 才写最少能用的。

## 2. 语言选择

| 运行环境 | 首选 | 可接受 | 不要 |
|---|---|---|---|
| 无操作系统的 MCU（RAM < 1 MB） | C、Rust（no_std） | — | 任何带 GC 或解释器的语言 |
| Linux 单板机上的常驻服务（rock-5b、树莓派这类板子上的设备程序） | Rust | Go、C++ | Python 做常驻服务（内存大、启动慢、GIL） |
| ROS 2 节点（机器人） | C++（实时、高频路径） | Python（胶水、工具、离线分析） | 在 Python 里做高频回调 |
| 服务器后端 / 云端 | Rust、Go | TypeScript、Kotlin | — |
| 脚本、工具、数据处理 | Python 3、POSIX shell | — | 超过 200 行的 shell；Python 2 |
| 网页前端 | TypeScript | — | 不带类型的 JS |

规则：
- 一个项目一个主语言。脚本可以用 Python/shell，但脚本同样过 lint（ruff / shellcheck）。
- 选择理由写成 `docs/adr/0001-language.md`（背景、候选、决定、后果）。
- 工具链版本固定并入库：`rust-toolchain.toml` / `.python-version` + 锁文件 / `go.mod`。
- 判断"最合适"问四件事：硬件装得下吗（内存、闪存、有无 OS）；这件事的生态在哪（驱动、库）；谁维护（你要能读懂日志、能跑起来）；项目里已经用了什么（少一种语言比多一种好）。

## 3. 仓库骨架

```

  LICENSE                 开源选 MIT/Apache-2.0；不开源写 "All rights reserved" 声明
  CLAUDE.md               给 AI 的项目说明，≤ 100 行，第一行 @ENGINEERING_STANDARD.md
  AGENTS.md -> CLAUDE.md  符号链接，给其他 AI 工具
  ENGINEERING_STANDARD.md 本文副本
  quality-budget.toml     量化门槛（第 17 节），CI 读取并强制
  docs/
    adr/                  架构决策记录：0001-language.md、0002-....md
    architecture.md       模块图 + 数据流 + 状态机（C4 的第 1、2 层就够）

    design/               M/L 级改动的设计便签（第 16 节），完成后归档或删除
```

## 4. 代码规则

- 格式化器 + linter 零警告，CI 强制：
  - Rust：`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings`；`clippy.toml` 设 `too-many-lines-threshold`、`cognitive-complexity-threshold`、`too-many-arguments-threshold`
  - Python：`ruff format --check`、`ruff check`（含 C901 复杂度、PLR 规则）、`mypy --strict`（至少对核心模块）
  - C++：`clang-format`、`clang-tidy`
  - Shell：`shellcheck`，每个脚本开头 `set -euo pipefail`
- 门槛（数值在 `quality-budget.toml`，默认）：函数 ≤ 50 行，文件 ≤ 500 行，参数 ≤ 5 个，嵌套 ≤ 3 层，圈复杂度 ≤ 10。超过要在审查里说明理由。
- 命名说清楚是什么，不自造缩写（行业通用的 `id`、`cfg`、`ctx` 可以）。物理量和时间带单位后缀：`timeout_ms`、`distance_m`、`temp_c`。
- 禁止：魔法数字（写成有名字的常量）；全局可变状态；吞掉错误；复制粘贴三次以上的代码；注释掉的代码（git 有历史）；没有调用者的代码。
- `TODO` 必须带日期和主题：`// TODO(2026-12-01 sensor): ...`。过期 TODO 由 CI 报错。
- Rust 专项：`unwrap()` / `expect()` 只在测试里，或旁边有注释说明"为什么不可能失败"；`unsafe` 块必须有 `// SAFETY:` 注释；`clone()` 不许用来绕过借用检查器；`#[allow(...)]` 必须带理由注释。
- 注释写"为什么"，不写"做了什么"。每个公共函数、类型、模块有一句话文档注释；模块级注释写明它的不变量（什么永远成立）。
- 一次任务只做一件事。顺手重构、顺手改格式、顺手升级依赖，都另开提交。
- **外科手术式改动**（Karpathy）：每一行改动都能追溯到任务要求。不"顺便改进"旁边的代码、注释、格式；不重构没坏的东西；跟随现有风格，即使你会写得不一样；看到无关的死代码，提一句，不删。你的改动造成的孤儿（没人用的 import、变量、函数）要清掉；原有的死代码不动，除非被要求。
- **写新代码前的阶梯**（ponytail），在第一个成立的地方停下：① 这段功能真的需要存在吗 ② 仓库里已经有了吗（helper、组件、模式） ③ 标准库有吗 ④ 平台原生有吗（systemd、journald、内核接口、浏览器原生控件） ⑤ 已装的依赖有吗（不为几行代码加新依赖） ⑥ 能一行写清吗 ⑦ 才写最少能用的代码，有逻辑分支就配一个小测试。
- **懒于写，不懒于读**：走阶梯之前先读改动触及的代码，列出所有要改到的地方（调用者、测试、夹具、配置、导出）。
- **懒而不是省**：信任边界的校验、数据丢失的错误处理、安全、无障碍、硬件校准、用户明确要的东西，永远不砍。
- **刻意的捷径要标记**：`// shortcut: <简化了什么>; 上限: <什么情况下不够>; 升级: <到时候怎么改>`。审计脚本会把它们汇总成债务台账；没写"升级"条件的捷径最容易烂在代码里，会被单独标出。

## 5. 模块化

- 一个模块 = 一个职责 + 一个小接口 + 能单独测试。公开的东西越少越好（指导值：公开函数 ≤ 10 个）。
- 好模块是"深"的：接口小，里面功能多。接口和实现一样大的模块是在浪费层。
- 依赖只能单向：`core`（纯逻辑）← `io`（硬件、网络、文件）← `app`（组装、命令行、配置）。核心逻辑不能 import 硬件和网络。
- 硬件和外部服务放在接口（Rust `trait` / Python `Protocol`）后面，测试用假实现替换。
- 模块之间用类型传数据（struct / dataclass），不传裸字符串和字典。
- 新增模块前先回答：删掉它项目还能用吗？能，就不要加。

## 6. 错误处理

- 错误必须带上下文：哪个文件、哪个设备、什么参数、在做什么。Rust：`thiserror` 定义错误类型，`anyhow::Context` 一路加上下文。
- 分两类处理：
  - 可恢复（网络抖动、设备暂时无响应）：重试（指数退避、有上限、抖动）、降级、记 `warn`。
  - 不可恢复（配置错、硬件消失、不变量被破坏）：记 `error`，进入安全状态（第 28 节），进程以非 0 退出，交给 systemd 重启。
- 对外 IO（网络、串口、I2C、CAN、文件）一律有超时和重试上限。没有超时的调用就是挂死的调用。
- 不吞错误：接住了必须二选一，要么处理掉，要么记日志后上抛。两者都不做的 `catch` / `let _ =` / `except: pass` 不许合并。
- 启动时校验全部配置和依赖资源，错了立刻报错退出，不要运行一半再炸。
- 面向用户的错误信息三段式：发生了什么、为什么、下一步做什么。

## 7. 日志与可观测性

- 结构化日志，每条包含：时间（UTC，ISO 8601）、级别、模块、消息、`key=value` 字段。
  - Rust：`tracing` + `tracing-subscriber`（`EnvFilter`，开发用 compact 格式，设备上用 json）。
  - Python：标准 `logging` + JSON formatter，或 `structlog`。
- 级别约定：
  - `error`：需要人处理，并且 runbook 里能查到怎么处理。
  - `warn`：异常但自动恢复了。
  - `info`：状态变化（启动、停止、配置加载、连接建立/断开、模式切换）。
  - `debug`：排错用的中间值。
  - `trace`：每个数据包、每次循环。
  - 默认 `info`；用环境变量（`RUST_LOG` / `LOG_LEVEL`）改级别，不改代码。
- 每个请求或任务一个 ID，贯穿所有相关日志，方便 grep。
- 日志去向：常驻服务写 stdout，交给 journald；用 `journald.conf` 的 `SystemMaxUse` 限制总量。必须写文件时按天轮转并限制保留份数。
- 闪存和 SD 卡设备：日志不写到会丢数据的介质（有的 SD 卡会静默丢写入；确认过不可信的介质写进项目 CLAUDE.md，绝不写那里）；高频日志放 tmpfs 或降频，避免写坏卡。
- 禁止：记密码、token、个人数据；在高频循环里打 `info`（需要时用采样或聚合计数）。
- 启动时打印一次：版本号、git 哈希、构建时间、生效配置（脱敏）、运行环境。
- 崩溃必留痕：panic / 未捕获异常的钩子把 backtrace 写进日志。
- 日志之外至少有：一个健康检查（`app --health` 或 `/health`），几个计数器（处理数、错误数、最近一次成功时间）。能回答"它现在活着吗、最近出过什么事"。

## 8. 测试

- 三层：
  - 单元：纯逻辑，无 IO，毫秒级，每次提交跑。
  - 集成：真文件、假硬件（接口的假实现），每次提交跑。
  - 端到端：真设备上的冒烟脚本（`scripts/smoke.sh`），每次部署后跑。
- 每个 bug 先写一个能复现它的测试，再修。修完测试变绿，这个 bug 永远不会回来。
- **红-绿-重构**（等级 2 起默认；等级 0/1 建议）：先写一个只测一个行为的小测试，运行并亲眼看它因为"功能还没有"而失败，再写最少的代码让它通过，全绿后才重构。测试一写就通过说明它测的是已有行为，不算数。先写了代码再补测试，补出来的测试只证明"代码做了什么"，不证明"代码该做什么"。
- **一次一个切片**：一个测试 → 一个最小实现 → 下一个测试，像曳光弹一样推进；不要先把所有测试写完再写所有实现，那是在测想象中的行为。
- **全量才算绿**：只改了一个文件也要跑项目的完整测试命令；看到的任何失败，包括不是你造成的，都按名字报告。
- 覆盖率：核心逻辑 ≥ 80%，总体 ≥ 60%。不为数字测 getter / setter。
- 测试必须确定性：不依赖当前时间、网络、执行顺序；用假时钟、假硬件。不稳定（flaky）的测试是 bug：隔离、限期修，不许用重试掩盖。
- 测试反模式，审查时直接打回：只在边界 mock（数据库、网络、文件、时间），不 mock 自己的业务逻辑；不测私有方法和实现细节（重构没改行为却红了就是信号）；断言不能用和被测代码一样的算法算出来，要用已知的字面值或规格里的值；不为了过 CI 跳过测试，`skip` / `#[ignore]` 必须带原因和到期日；测试专用代码不塞进生产代码；测试里不用固定 sleep 等待，用条件轮询。
- 解析外部输入的代码（协议、配置、文件格式）必须有基于属性的测试（Rust `proptest` / Python `hypothesis`），能接触不可信输入的还要做模糊测试（`cargo fuzz`）。
- 状态机必须有覆盖全部转换的测试，非法转换也要测。
- 严格级：核心模块跑变异测试（`cargo-mutants` / `mutmut`），杀灭率 ≥ 70%；低于说明测试只是在"跑过"代码而不是在"检查"代码。
- 测试命名说明场景和预期：`应在设备超时后重试三次`。
- 测试跑在每次提交（CI 或 pre-commit）。失败不许合并，没有例外。
- 性能相关的改动必须附 benchmark 前后数据（Rust：`criterion`），否则按普通重构审查。
- **排错六步**（superpowers systematic-debugging、Pocock diagnosing-bugs、Osmani debugging 三者的交集），顺序不能跳：
  1. 先建反馈回路：一条命令能稳定地在这个 bug 上变红（失败的测试、curl 脚本、对比快照的 CLI、重放）。建不出回路就说明试了什么，要环境、要日志或要加探针的许可；没有回路不许假设。
  2. 复现并最小化：确认它红的是用户报的那个症状，不是旁边的；一次去掉一个元素，直到剩下的每个都不可少。
  3. 读完整的错误信息和栈，查最近改动（回归用 `git bisect`），对比仓库里能工作的相似代码，列出所有差异，再小的差异也不假设"不可能有关"。
  4. 写下 3–5 个可证伪的假设（"如果 X 是原因，那么改 Y 就会消失"）并排序，一次只改一个变量验证；不懂就说"我不理解 X"，不假装。
  5. 找到根因再修：先写回归测试看它红，只修根因，不夹带"顺便"的改动，然后全量测试，再跑一次第 1 步的回路。修复失败不到 3 次回到第 1 步；3 次仍失败，停下来质疑架构并和用户讨论，不试第 4 次。
  6. 清理：删掉带唯一前缀的调试日志（如 `[DEBUG-a4f2]`）和临时脚本，提交信息里写明根因。"找不到根因"的情况 95% 是调查不完整；确属环境或时序问题的，记录调查过程并加重试、超时、监控。

## 9. 版本控制与提交

- 所有东西入 git，除了：密钥、构建产物、大二进制（> 1 MB 用 LFS 或放外面）。
- 一个提交一件事。提交信息用 Conventional Commits：
  `feat(lighting): 支持色温渐变` / `fix(sensor): I2C 超时后重试` / `docs:` / `refactor:` / `test:` / `perf:` / `chore:` / `build:` / `ci:`
- 提交信息正文写"为什么"，并引用任务或 ADR。
- `main` 永远可发布。工作在短分支，合并前过 CI 和审查。单次合并 ≤ 400 行 diff（不含生成文件、锁文件）；大了拆。
- 发布打 tag `vX.Y.Z`（SemVer：不兼容改动升 X，加功能升 Y，修 bug 升 Z）。
- 不得重置、覆盖、删除别人的未提交改动；不得大范围"顺手"格式化。
- 仓库里跑密钥扫描（`gitleaks`）；一旦泄露，视为已失效，立即轮换，不靠删历史。
- **提交门禁**：`.githooks/pre-commit` 在提交前跑 `scripts/ci.sh`，不绿不提交；每个克隆跑一次 `scripts/install-hooks.sh` 安装。`--no-verify` 一律不许；太慢的检查挪到 CI（第 17 节），不是关掉门禁。

## 10. 文档

- `README.md` 回答四件事：是什么、怎么跑、怎么测、怎么部署。
- `CHANGELOG.md` 用 Keep a Changelog 格式，和代码同一提交更新：
  ```
  ## [Unreleased]
  ### Added
  - 色温渐变（#12）
  ### Fixed
  - I2C 超时后不再卡死（#15）

  ## [1.2.0] - 2026-11-01
  ...
  ```
  分组固定为 Added / Changed / Deprecated / Removed / Fixed / Security。
- ADR（`docs/adr/NNNN-标题.md`）：每个重要决策一个文件，四段：背景、候选方案、决定、后果。旧 ADR 不改，被取代时新文件注明"取代 0003"。
- `docs/runbook.md`：部署步骤、回滚步骤、日志在哪看、每个 `error` 级日志对应怎么处理。出过的故障都要进去。
- `docs/pitfalls.md`：失误登记（症状、原因、怎么避免）。同类第二次 ⇒ 改成自动检查并从这里划掉。
- 文档分四类，不混写（Diátaxis）：教程（带着做）/ 操作指南（解决一个具体问题）/ 参考（API、配置项）/ 解释（为什么这样设计）。
- 文档里的代码示例要能跑（Rust 用 doctest；其他语言用 CI 跑示例）。
- 文档和代码同一提交改；审查时对照检查。

## 11. 配置与密钥

- 配置来源优先级：命令行参数 > 环境变量 > 配置文件 > 内置默认值。
- 每个配置项都有默认值、类型和范围校验；启动时打印最终生效配置（脱敏）。
- 密钥只放环境变量或权限 600 的文件；永不入库、永不进日志、永不出现在聊天回复里。仓库里放 `config.example.toml`。
- 同一份二进制在开发机、测试、设备上只靠配置区分，不靠改代码。
- 配置文件带 `version` 字段（第 23 节）。

## 12. 构建、发布、部署

- 可重现：锁文件入库、工具链固定、一条命令出产物（`scripts/build.sh`）。两次构建同一提交得到同样的产物。
- 构建机和设备分开：在构建机上构建，设备只安装产物。设备上禁止编译。
- 产物自带身份：`app --version` 打印版本、git 哈希、构建时间。产物附 SHA256，设备端安装前校验。
- 部署脚本幂等；保留上一个版本；`scripts/rollback.sh` 一条命令回滚；部署后自动跑健康检查和冒烟测试。
- 安全最低线：
  - 依赖审计进 CI：`cargo audit` + `cargo deny` / `pip-audit` / `npm audit`。
  - systemd 服务最小权限：专用用户、`ProtectSystem=strict`、`ProtectHome=yes`、`NoNewPrivileges=yes`、`PrivateTmp=yes`，只放开需要的设备和目录。
  - 外部输入（网络、串口、文件、用户）在进入系统的边界处校验。
  - 不从不可信来源下载并执行脚本（`curl | sh`）；安装脚本固定版本和校验和。
  - 等级 3：静态安全扫描（semgrep 默认规则集或 CodeQL）进 CI；涉及安全的改动再由第二个独立模型审一次（Trail of Bits 的 second-opinion 做法）。

## 13. 审查（人或 AI）

- 顺序：格式、lint、测试、审计、质量门槛全绿 ⇒ 才进入审查。审查不讨论机器已经检查的东西。
- AI 审查的前提：有本文、有 diff、有变更说明（第 31 节）、有测试输出。四样缺一样，审查等于猜。
- 用和作者不同的模型或至少不同的会话做审查（盲区不同）。例如：Claude Code 写，`/code-review` 或另一个模型审；L 级改动用多代理审（`/code-review ultra`）。
- 审查清单（每条要么打勾，要么给出 文件:行号）：
  1. 改动做了声明的事，而且只做了这件事？
  2. 新行为和修的 bug 有测试覆盖？测试会在改动回退时变红？
  3. 错误路径都处理了：超时、空输入、设备断开、磁盘满、断电、并发？
  4. 日志够定位问题，但不过量、不泄密？
  5. 模块边界没被打穿（core 没有 import io）？
  6. 文档、CHANGELOG、runbook 更新了？
  7. 有更简单的写法？有重复代码？
  8. 安全：注入、密钥、权限、输入校验、新依赖？
  9. 性能改动有前后数据？资源预算没超？
  10. 持久化格式改了的话，兼容和迁移处理了？
- 严重度：`blocker`（不修不合并）/ `should`（本次修）/ `nit`（可选）。
- 审查的优先级（ponytail-review）：正确 > 安全 > 扛得住负载 > 有测试 > 快 > 精简。精简排最后，但必须查：死代码、重造已有 helper 或标准库、不必要的抽象、近似重复、一个函数干几件事。
- 每条发现都要有一个具体的失败场景（什么输入或状态 → 什么后果）。给不出场景的是风格意见，不进清单。
- 建议的修法取最小的那个，能删代码的优先于加代码的。
- 结尾三行：结论（能不能合）、可删除的行数或依赖、没检查什么。
- 作者必须逐条回应每个发现：已修（提交哈希）/ 不修（理由）/ 延后（登记任务）。不许静默忽略。
- 作者收到发现后：先核实再改（对照代码验证审查者的说法），说错了就用技术理由反驳并给证据；不做表演性同意（"你说得对！"），不批量改，一条一测。
- 分两个轴报告，互不掩盖：需求轴（做了声明的事？多做了？少做了？）和规范轴（符合本文和仓库约定？）。代码可以完美符合规范却做错了东西，反之亦然。
- AI 写的代码需要更多审查，不是更少。"AI 生成的应该没问题"不是理由。
- 审查的发现如果是通用问题，变成 lint 规则或测试，而不是只在这次修掉。
- 审查者提示词和完整协议见 `review-protocol.md`（第 30 节）。

## 14. 完成的定义（Definition of Done）

按项目等级缩放（第 0 节）：等级 0 只要求代码、无密钥、如实汇报三项；等级 1 不要求真机部署。等级 2 起全部打勾：

- [ ] 任务有书面验收标准（第 15 节），改动做的就是这些
- [ ] 代码写完，格式、lint、质量门槛零警告
- [ ] 代码实际运行并观察过行为，不只是编译或类型检查通过
- [ ] 没有残留的调试输出、注释掉的代码、临时文件、未删的 `[DEBUG-...]` 日志
- [ ] 单元 + 集成测试通过；修 bug 的任务有复现测试
- [ ] README / 文档 / CHANGELOG / runbook 按需更新，和代码在同一提交；文档描述现状，不叙述改动历史
- [ ] 至少一次独立审查，`blocker` 清零，`should` 已修或有书面理由，每条发现都有回应
- [ ] 在构建机构建出带版本号和校验和的产物
- [ ] 在目标设备上部署，健康检查和冒烟测试通过（真机；模拟不算）
- [ ] 提交信息规范，已合并到 `main`，必要时打 tag
- [ ] 变更说明（第 31 节）写明：验证了什么、怎么验证的、没验证什么

# 第二部分 严格级要求

默认全部启用。关闭某一条必须写 ADR。

## 15. 需求与验收先行（Definition of Ready）

- 没有验收标准不开工。每个任务动手前写清（放 `docs/tasks/YYYY-MM-DD-<slug>.md` 或 issue）：
  - 目标：一句话。
  - 验收标准：可执行的检查清单或 Given/When/Then。
  - 非目标：明确不做什么。
  - 影响范围：哪些模块、接口、配置、数据格式。
  - 测试计划：哪一层测、怎么测。
  - 回滚方案：出问题怎么退回。
- 验收标准必须能变成测试。写不出测试的验收标准就是没想清楚。
- **想清楚再动手**（Karpathy）：把假设写出来；有多种理解就列出来让用户选，不悄悄挑一个；有更简单的做法就说，必要时反驳；哪里不清楚就停下来点名问。把任务改写成可验证的目标："加校验" → "先写无效输入的测试，再让它通过"；"修 bug" → "先写复现测试，再让它通过"；"重构" → "前后测试都绿"。
- **像审问一样把设计问清楚**（Pocock grilling、superpowers brainstorming）：把设计看成一棵决策树，只问前置条件已定、现在就能答的问题，每个问题附上推荐答案，让"是"就等于接受推荐；事实类问题（环境、现有代码）自己查，不问用户，决策类才问；先读过上下文再问，不问上下文里已有答案的事；默认值要说出口；用户对一个想法说"听起来不错"不等于批准了设计文档；可以用一次性 spike 原型验证想法，但要留下来必须重新过设计关。
- 模糊的要求先问清，不猜。用户不在线时按最保守的解释执行，并在变更说明里写明假设。
- 任务大小 ≤ 1 天工作量、≤ 400 行 diff。大了拆成能各自发布的小任务。

## 16. 设计先行与变更分级

| 等级 | 定义 | 要求 |
|---|---|---|
| S | 单模块内部，不改接口，≤ 100 行 | 直接做，走标准审查 |
| M | 跨模块，或改接口 / 配置键 / 数据格式，≤ 400 行 | 先写设计便签（≤ 1 页：问题、候选、选择、风险、测试计划）再写代码 |
| L | 新子系统、换依赖、数据迁移、影响安全或持久化数据 | 设计便签 + ADR + 分阶段计划（每阶段可独立发布、可回滚），逐阶段审查 |

- M/L 级改动的第一个提交是设计文档，不是代码。设计便签放 `docs/design/`，完成后归档进 ADR 或删除，不留过期设计。
- 等级 0/1 的项目：M 级只需在变更说明里写三行（问题、选择、风险），不单独建文件。
- **计划写给没看过代码的人**（superpowers writing-plans）：每个任务小到能独立验证、独立被否决（几分钟一个），写明要建或改的文件、接口签名、测试名和断言、验证命令和预期输出；计划不能比它描述的代码还长；禁止"待定"、"处理边界情况"这类空话。
- 变更等级写进变更说明；审查者先核对等级对不对。

## 17. 质量门槛量化

- 每个项目根目录有 `quality-budget.toml`，CI 读取并强制。默认值：

| 指标 | 默认门槛 |
|---|---|
| 编译 / lint 警告 | 0 |
| 测试通过率 | 100% |
| 核心模块行覆盖率 | ≥ 80% |
| 总覆盖率 | ≥ 60% |
| 函数圈复杂度 | ≤ 10 |
| 函数行数 / 文件行数 / 参数个数 | ≤ 50 / ≤ 500 / ≤ 5 |
| 单次合并 diff | ≤ 400 行 |
| 重复代码 | ≤ 3% |
| 高危依赖漏洞 | 0 |
| 已知 flaky 测试 | 0 |
| 过期 TODO | 0 |
| 核心模块变异杀灭率 | ≥ 70% |

- **没有检查命令的数字是愿望，不是门槛**（Osmani constraint-driven-development）：`quality-budget.toml` 里每个有数字的门槛都对应 `scripts/ci.sh` 里一条真正会变红的命令；启用前先用故意违规的样例确认它会红，再用干净样例确认它会绿。
- **棘轮**：没有目标值的指标先记录今天的值，规则是"不许变差"；达标后再定目标。
- **门槛只能变严。** 收紧悄悄做；放松必须大声：写 ADR，并且不允许和导致失败的那个改动同一提交。
- **例外有期限**：对某规则、某路径的豁免写进 `[[exceptions]]`（规则、路径、原因、到期日 ≤ 90 天），到期审计报错。
- **至少一条外部检查**（依赖漏洞扫描、静态分析这类不是项目自己写的检查），因为项目自己的测试是"自己检查自己"。
- 审查时专门盯五种绕过：阈值被移动、测试被弄简单（skip、删断言、删测试文件）、检查器被静音（新增 `#[allow]`、`# noqa`、`eslint-disable`、`nosemgrep`）、工作没做完（抛异常的桩、空 catch、用 TODO 代替实现）、凭空出现的例外。`--no-verify` 一律不许。
- 度量工具：Rust `cargo llvm-cov`、clippy 阈值、`cargo-mutants`；Python `coverage`、`ruff`（C901 / PLR）、`mutmut`；通用 `jscpd` 查重复；`scripts/audit_project.py` 查结构、TODO、文件长度。

## 18. 资源预算（设备和常驻程序）

- 每个常驻程序在 `quality-budget.toml` 的 `[resources]` 里定义并测量：二进制大小、启动到就绪时间、空闲 CPU、空闲 RSS、峰值 RSS、每日写盘量、功耗（有条件时）。
- 冒烟测试测这些数字；超预算 = 冒烟失败。
- 每次发布前对比上一版本快照（第 26 节），任何指标恶化 > 10% 必须解释或修。
- 示例（小型 Linux 设备，按项目实测后定）：空闲 CPU ≤ 2%、RSS ≤ 50 MB、每日写盘 ≤ 10 MB、启动到就绪 ≤ 3 s。

## 19. 可靠性与断电安全

- 假设随时断电。所有持久化写入：写临时文件 → `fsync` → `rename` 原子替换 → `fsync` 目录。永不原地改写配置或状态文件。
- 状态文件带版本号和校验和（CRC32 / SHA-256）；损坏时回退到上一份或默认值并记 `error`，不能因此起不来。
- 启动幂等：重复启动、半完成的任务、残留的临时文件都要能处理。
- 优雅退出：处理 `SIGTERM`，≤ 5 s 内收尾；systemd `TimeoutStopSec` 与之匹配。
- 看门狗：常驻服务用 systemd `Type=notify` + `WatchdogSec` + `sd_notify`，主循环卡死自动重启；`Restart=on-failure` 配合 `StartLimitIntervalSec` / `StartLimitBurst` 防止无限重启风暴。
- 磁盘满、只读文件系统、SD 卡掉线、时间跳变、内存压力，每一项至少有一个自动化测试或冒烟项（第 28 节清单）。
- 单点故障清单写进 `docs/architecture.md`：哪个部件坏了会怎样、怎么发现、怎么恢复。

## 20. 并发与时间

- 共享可变状态必须有唯一所有者；跨线程只传消息或不可变数据。
- 每个锁都有获取超时或文档化的锁顺序；持锁时不做 IO。
- async 代码里不阻塞（无 sleep、阻塞 IO、长计算）；阻塞工作交给专用线程池。
- 每个外部资源（串口、CAN、I2C 总线、文件）只有一个写者。多个写者的"协调"迟早失败。
- 内部一律 UTC，只在边界转时区；持续时间和超时用单调时钟（`Instant`），永不用墙钟。
- 重试的操作必须幂等；非幂等操作用唯一 ID 去重。
- 后台任务有取消机制和退出确认，不留"僵尸"线程。

## 21. 依赖与供应链

- 每加一个依赖要回答四个问题并写进提交说明：为什么不自己写 50 行？最近一年有发布吗？许可证兼容吗？带进来多少传递依赖？
- 升级依赖也是你没写的行为变更：看 changelog 和 advisories，一包一提交，跑全量测试；不接受"只是升个版本"。
- 锁文件入库；CI 用 `--locked` / `--frozen`。
- 依赖审计（漏洞 + 许可证 + 重复版本）每次提交跑；每月一次依赖更新，单独提交，跑全量测试。
- 产物附 SHA256 和 SBOM（`cargo cyclonedx` / `syft`）。
- 不在仓库里放来历不明的二进制；必须放的记录来源和校验和。
- 构建脚本不联网下载未固定版本的东西。

## 22. 数据、备份与隐私

- 数据分类写进 `docs/architecture.md`：个人数据 / 设备状态 / 可再生数据。个人数据最小化，不记日志、不出设备（除非用户明确同意）。
- 重要状态有异地备份（不在同一张卡、同一台设备上）；备份自动校验；每季度做一次真实恢复演练。没恢复过的备份等于没有备份。
- 确认过会丢数据的介质（某些 SD 卡、U 盘）列为不可信，任何备份、归档、日志不写它；清单放项目 CLAUDE.md。
- 日志、备份、临时文件都有最大保留期或容量，自动清理。
- 敏感数据静态加密时，密钥不与数据同处。

## 23. 兼容性与迁移

- 所有持久化格式（配置、状态文件、数据库、协议消息）带 `version` 字段。
- 新版本必须能读旧数据（向后兼容 ≥ 2 个版本）；迁移脚本幂等，先备份再迁移，可回滚。
- 回滚后旧程序要么能读新数据，要么明确拒绝并说明；不能静默损坏。
- 对外接口（CLI 参数、配置键、协议）改动走废弃流程：标记废弃 → 至少一个版本期打 `warn` → 删除；记入 CHANGELOG 的 Deprecated / Removed。
- 兼容性测试：用上一版本的真实配置和状态文件跑一遍。

## 24. 发布纪律

- `docs/release-checklist.md` 逐项打勾才能发：CI 全绿、CHANGELOG 移到版本段、版本号按 SemVer、tag、产物校验和、冒烟通过、runbook 更新、回滚方案实际演练过、资源预算未超。
- 分阶段：先 1 台设备观察一个完整使用周期（≥ 24 h），再全量。
- 发布前写明回滚判据（哪些指标或现象触发回滚）；观察窗口内有自动检查或有人盯着。
- 热修也走完整流程，只是更快；不允许直接在设备上改代码或改产物。
- 发布记录：谁、何时、哪个版本、哪些设备、结果；写进 CHANGELOG 版本段或 `docs/releases/`。

## 25. 接口契约

- 所有对外接口都有参考文档并被测试覆盖：
  - CLI：`--help` 完整；退出码 0 成功 / 1 一般错误 / 2 用法错误；脚本模式不交互；`--version`、`--health`。
  - 配置：每个键写明类型、默认值、范围、含义。
  - 协议 / 消息：schema 文件入库，带版本。
  - 文件格式：版本 + 示例文件入库。
- 接口改动至少是 M 级变更（第 16 节）。

## 26. 代码健康度趋势

- 每次发布把度量快照（行数、复杂度、覆盖率、依赖数、警告数、TODO 数、资源指标）写进 `docs/metrics/YYYY-MM-DD-vX.Y.Z.md`。
- 指标只许往好的方向走；恶化必须在发布说明里解释。
- 每季度一次减负任务：删死代码、删无用依赖、合并重复、清过期 TODO。

## 27. 事故复盘

- 任何真机或线上故障，24 小时内写 `docs/postmortems/YYYY-MM-DD-<slug>.md`：时间线、影响、根因（连问五个为什么）、为什么测试和监控没拦住、行动项（每条有期限）。
- 不追责，追系统。
- 每个行动项最终落到：一条测试 / 一条告警 / 一条 lint / 一条 runbook 条目。只写"以后注意"不算完成。
- 同类第二次发生 ⇒ `pitfalls.md` 条目升级为自动检查（第 0 节规则 5）。

# 第三部分 设备与嵌入式专项

## 28. 设备软件

- **安全状态**：每个设备定义"安全状态"并写进 `docs/architecture.md`（例如台灯：保持当前亮度或温和关闭；机器人：停车并保持制动）。任何未处理错误、看门狗触发、通信丢失都进入安全状态。进入路径不依赖网络、配置或复杂逻辑。
- **硬件抽象层**：所有硬件访问经 trait / 接口；提供模拟实现，CI 不需要硬件也能跑 90% 的测试。
- **显式状态机**：设备模式用枚举状态机，转换表写进 `docs/architecture.md`；非法转换是错误，不是静默忽略。
- **无网络、无时钟**：启动不依赖网络；NTP 不可达时功能降级但不崩；没有 RTC 时时间戳标记"未同步"。
- **升级与回滚**：当前 / 上一版本双目录（或 A/B 分区）+ 一键切换；升级中断电可恢复；升级后健康检查失败自动回退。
- **恢复通道**：串口或 SSH 兜底，服务挂了也能进；出厂重置路径文档化并测试过。
- **闪存寿命**：减少写入（日志降频或放 tmpfs、状态合并写）、根文件系统只读（可选）、监控每日写入量。
- **故障注入清单**（每项至少一个自动化测试或冒烟项）：拔线、断电、总线错误、设备无响应、磁盘满、只读文件系统、时间跳变、内存压力、网络消失后恢复。
- **现场操作安全**（机器人类）：有人值守；物理急停优先；软件不得绕过硬件互锁；唯一控制权持有者；软件测试不能记为真车轮次。

# 第四部分 AI 会话工作规则

## 29. AI 作者规则

- 四条工作习惯（Karpathy）：想清楚再动手（第 15 节）；最少的代码（第 4 节阶梯）；外科手术式改动（第 4 节）；目标驱动，多步任务每步写明怎么验证，验证标准强才能自己循环到做完，弱（"让它能用"）就只能反复问。
- 每次回复的最后一两行：跳过了什么、没检查什么、用户该知道的风险（ponytail 的披露习惯）。写在变更说明的"没验证什么"和"跳过了什么"里。
- 开工前读：项目 `CLAUDE.md`、本文相关章节、`docs/pitfalls.md`、`docs/runbook.md`。写出任务的验收标准和假设（第 15 节）。
- 不猜 API：用不熟的库先查文档、源码或 `cargo doc`。同一个编译或测试错误连续 3 次没解决，停下来报告，不要盲试第 4 次。
- 不为了过检查而降低检查：不删测试、不标 ignore、不放宽 lint、不加 `#[allow]` / `# noqa` / `as any`（除非附理由注释并在变更说明里列出）。
- 一次任务只做一件事。顺手发现的问题登记到 `pitfalls.md` 或作为独立建议提出，不夹带进本次改动。
- **验证后再说完成**（superpowers verification-before-completion）：声称"测试通过 / 构建成功 / bug 修好 / lint 干净"之前，必须在本条消息里新跑对应命令、读完输出、看退出码。上一轮的结果、"应该可以"、"大概没问题"、"linter 过了所以能编译"、"子代理说成功了"都不算证据；看到自己写出"应该、大概、似乎"，就是停下来跑命令的信号。所有"测试通过"附实际命令和输出摘要；没跑的写"未验证"。模拟 / 本地 / dry-run ≠ 真机。
- **早纠偏**（Claude Code 官方实践）：发现方向错了立刻停下回到计划，不在错的基础上堆修正；长会话质量会下降，一个任务结束就清上下文或开新会话，跨会话用交接文档。
- **机器能定的规则放进配置，不放进提示词**（Claude Code 官方实践）：权限、禁止的命令、格式化、"结束前必须跑检查"这类不能有例外的规则用 hook、deny 规则和 settings 强制；提示词和 CLAUDE.md 是给可以有例外的指导用的。一条 CLAUDE.md 规则反复加粗还是被漏掉，就说明它该是 hook。反过来，只是偏好的东西不要做成 hook；强制的东西保持少，每条都会误触发、都要有人维护。
- **请求审查时说明"跳过风格"**：被要求找问题的审查者总能找到点什么；每条都改，就会多出抽象层和为不可能的情况写的测试。让审查者只报影响正确性、安全、可维护性的问题。
- 项目 `CLAUDE.md` 只写 AI 自己读代码发现不了的东西：确认工作的确切命令（测试、类型检查、lint、跑单个测试文件）、不成文的约定、踩过的坑，以及纠正过两次的事。
- 不碰的东西：用户未提交的改动、他人分支、设备上的数据、密钥。不重置、不覆盖、不大范围格式化。
- 密钥永不出现在回复里；需要用户输入密码时给一条可直接运行的命令，结果自己读。
- 遇到规则冲突按第 1 节优先级取舍，并在变更说明里写明。
- 项目 `CLAUDE.md` ≤ 100 行，只放每次都需要的规则，其余指向文档。
- 汇报用第 31 节的变更说明模板，不用别的格式。

## 30. AI 审查规则

- 审查者与作者不同模型，至少不同会话、不带作者上下文。
- 输入四样：本文、diff、变更说明、测试输出。缺一样先要，不猜。
- 按第 13 节清单逐条对照；每条发现给 文件:行号、问题、违反的条款、建议改法、严重度。
- 不复述改动，不表扬，找不到问题就明说"未发现 blocker"。
- 最多三轮；第三轮仍有 blocker，升级给用户决定。
- 完整提示词和输出格式见 `review-protocol.md`。

## 31. 变更说明模板

每次改动的汇报用这个格式，一项都不省：

```
## 变更说明
- 做了什么：
- 为什么：（关联任务 / issue / ADR）
- 变更等级：S / M / L
- 影响范围：模块、接口、配置、数据格式
- 怎么验证的：命令 + 结果摘要（真实输出）
- 没验证什么：
- 风险与回滚：（可逆性：双向门可回滚 / 单向门不可逆并说明；影响半径一个词）
- 文档 / CHANGELOG：已更新 / 不需要（理由）
- 新依赖：无 / 名称 + 四个问题的答案（第 21 节）
- 假设：（用户不在线时按什么解释执行的）
- 跳过了什么：（按等级或判断跳过的流程，一句话说明理由）
```

## 附录 B：新项目第一天要做的事（按顺序）

1. `git init`，用 skill 的 `scripts/bootstrap_project.sh` 建第 3 节的骨架（含本文副本和 `audit_project.py`）。
2. 定项目等级（第 0 节），写 ADR-0001 选语言，固定工具链版本，填 `quality-budget.toml`（含 `[project] tier`）。
3. 让 `scripts/ci.sh` 在空项目上先跑绿。
4. 写 `config.example`、日志初始化、`--version`、`--health`，让空程序先能启动、能打日志、能优雅退出。
5. 写 `build.sh`、`deploy.sh`、`rollback.sh`、`smoke.sh`，在设备上部署一次"Hello"版本，实际演练一次回滚。
6. 定义安全状态和故障注入清单（第 28 节），至少把"断电"和"设备无响应"两项的测试写出来。
7. 以上全部通过后，才开始写第一个功能。

## 附录 C：术语

- **ADR**：Architecture Decision Record，架构决策记录。一个决定一个文件。
- **CI**：持续集成。每次提交自动跑格式、lint、测试、审计的流程。
- **DoR / DoD**：Definition of Ready / Done。开工条件 / 完成条件。
- **SemVer**：语义化版本号 X.Y.Z。
- **SBOM**：软件物料清单，列出产物里所有依赖及版本。
- **冒烟测试**：部署后在真机上跑的最小一组检查，确认"基本能用"。
- **变异测试**：故意改坏代码，看测试会不会变红；不变红说明测试没真正检查。
- **幂等**：同一个操作执行多次和执行一次结果相同。
- **项目等级**：0 脚本 / 1 工具 / 2 产品设备 / 3 安全运动金钱。决定本文有多少条生效（第 0 节）。
- **shortcut 标记**：代码里刻意留下的简化，注释写明上限和升级条件，审计脚本汇总成债务台账（第 4 节）。
- **红-绿-重构**：先写会失败的测试（红），写最少代码让它过（绿），再整理（重构）。
- **反馈回路**：一条能在某个 bug 上稳定变红的命令；排错的起点。
- **棘轮**：记录今天的指标值，只许变好不许变差。
