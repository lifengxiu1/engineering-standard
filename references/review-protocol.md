# 审查协议（人或 AI）

适用：任何将要合并到 `main` 的改动。审查者可以是人、`/code-review`，或另一个模型的会话。
对应标准第 13 节和第 30 节。

## 1. 前提

- 审查者与作者不同模型；至少不同会话、不带作者上下文。同一个会话自己审自己，盲区完全重合，不算审查。
- 格式、lint、测试、审计、质量门槛已全绿（`scripts/ci.sh` 退出 0）。没绿先打回，不审。
- 四样输入齐全：`ENGINEERING_STANDARD.md`、diff、变更说明（标准第 31 节）、测试输出。缺一样先要，不猜。

## 2. 给审查者的提示词（直接粘贴）

```
你是独立审查者。请按 ENGINEERING_STANDARD.md 审查下面的改动。
输入：标准全文、diff、变更说明、测试输出。
先核对两件事：变更等级（S/M/L）定对了吗？变更说明里"怎么验证的"有真实命令和输出吗？
再按标准第 13 节的 10 条清单逐条对照，并额外检查：
  第 19 节（断电与原子写）、第 20 节（并发与时间）、第 21 节（新依赖）、
  第 23 节（持久化格式兼容）、第 18 节（资源预算）。
先分两个轴看，一个轴过了不能掩盖另一个轴：需求轴（做了声明的事？多做了？少做了？）、规范轴（符合标准和仓库约定？）。
专门盯五种绕过：阈值被移动、测试被弄简单、检查器被静音、工作没做完、凭空出现的例外。
输出：按严重度排序的表格，列：严重度 | 文件:行号 | 问题 | 违反条款 | 建议改法。
严重度：blocker（不修不合并）/ should（本次修）/ nit（可选）。
只报告能指出具体位置、并能写出具体失败场景（什么输入或状态 → 什么后果）的问题；不复述改动，不泛泛表扬。
修法取最小的那个，能删代码的优先。
对"缺测试"的发现，写出该测的场景，不要只说"加测试"。
找不到问题就明说"未发现 blocker"，不要硬凑。
结尾三行：结论（能不能合并）、可删除的行数或依赖、没检查什么。
最后一行写：blocker N 条，should N 条，nit N 条。
```

## 3. 输出格式

| 严重度 | 位置 | 问题 | 条款 | 建议 |
|---|---|---|---|---|
| blocker | src/sensor.rs:17 | 对串口输入直接 `unwrap()`，坏行会让进程崩溃 | §4 Rust 专项、§6 | 返回 `Result`，坏行记 `warn` 并跳过 |
| should | src/sensor.rs:25 | 主循环里每次读数打 `info` | §7 | 改 `debug`，或每 60 s 聚合一条 |

结尾：`结论：修掉 blocker 后可合并 · 可删 0 行 · 未检查：真机行为`，最后一行 `blocker 1 条，should 1 条，nit 0 条`。

## 4. 作者回应规则

- 先核实再改：对照代码验证审查者的说法；验证不了就说验证不了，问怎么办。说错了用技术理由反驳并给证据（代码、测试）。
- 不做表演性同意（"你说得对！""好观点！"），直接说改了什么或为什么不改。不批量改，一条一测。
- 每条发现必须回应，三选一：已修（提交哈希）/ 不修（理由）/ 延后（登记到 issue 或 `docs/pitfalls.md`）。
- 不许静默忽略；不许用"这是老问题"回避 blocker。老问题被本次改动触及，就是本次的问题。
- 回应写在变更说明末尾的"审查回应"段。
- 回应后审查者复核 blocker；最多三轮。第三轮仍有 blocker，升级给用户决定。

## 5. 审查者自律

- 优先级（ponytail-review）：正确 > 安全 > 扛得住负载 > 有测试 > 快 > 精简。先找会坏的，再找多余的。
- AI 写的代码需要更多审查，不是更少；依赖版本升级也是没人写过的行为变更，要看 changelog。
- 区分本次改动引入的问题和原来就有的问题；原有问题被本次改动触及才算本次的。不为凑数编造发现。
- 只看 diff 和它触及的上下文；不借审查之名要求无关重构（那是另一个任务）。
- 发现是通用问题（不止这一处会犯）⇒ 单独列出"建议升级为自动检查"的条目：lint 规则、测试或 `audit_project.py` 的检查项。
- 严重度要诚实：把 nit 标成 blocker 会让作者不再信任审查。

## 6. 严重度判定

- **blocker**：正确性错误；数据可能损坏；密钥或安全问题；无测试的新行为；吞错误；没有超时的 IO；对外部输入 `unwrap`；持久化格式改了没兼容；feat/fix 没更新 CHANGELOG；变更说明里的验证不是真实输出。
- **should**：可读性；重复代码；日志不足或过量；文档缺失；命名；小的性能退化；变更等级定低了。
- **nit**：风格偏好、措辞。
- 风格意见和写不出具体失败场景的担忧不进清单。请求审查时明说"跳过风格"：被要求找问题的审查者总能找到点什么，全改会多出抽象层和没用的测试。

## 7. 在 Claude Code 里怎么做

1. 作者会话按工作流 C 做完，写好变更说明，`scripts/ci.sh` 全绿。
2. 新开一个会话（或用 `/code-review`；L 级改动用 `/code-review ultra` 多代理云端审查），把第 2 节的提示词连同四样输入交给它。
3. 作者会话收到清单后按第 4 节逐条回应，把回应写进变更说明末尾。
4. blocker 清零后才能合并。
