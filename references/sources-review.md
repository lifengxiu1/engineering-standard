# 外部 skills 评估记录

日期：2026-11-02。本文回答"某条规则从哪来、为什么取或弃了某个外部 skill"。用户的要求是"明辨是非后融合"，所以每一条都写了取舍理由。

## 评估标准（五问）

1. 针对的是 AI 写代码的真实失误吗？要有清楚的因果或作者给出的证据，不是口号。
2. 通用吗？绑定某个框架、语言或公司流程的不取。
3. 和本标准的原则冲突吗？正确 > 可读 > 简单 > 快；YAGNI；外科手术式改动；如实汇报。
4. 开销和收益成比例吗？会不会把上下文塞满、把每个小任务变成仪式？
5. 能变成可检查的东西吗（测试、脚本、清单），还是只能靠自觉？能检查的优先。

怎么读的：每个仓库都直接读了 SKILL.md 原文（superpowers 7 个、mattpocock 7 个、addyosmani 6 个含参考清单、Karpathy 1 个、ponytail 4 个），不以 star 数为准。各聚合站报的 star 数互相矛盾（同一个仓库从 4 万到 25 万都有），只能当"很流行"看，不能当证据。

## 逐个评估

### obra/superpowers（Jesse Vincent）

是什么：14 个 skill 组成的强制工作流：brainstorming → 设计文档 → writing-plans → 执行（子代理或本会话）→ TDD → 审查 → 收尾。哲学是"证据胜于声称"、"流程胜于猜测"。

取：
- TDD 的核心判断"没看着测试失败，就不知道它测的对不对"；"一写就过的测试测的是已有行为"；全量测试才算绿；"修 bug 先写复现测试"。
- 排错四阶段（根因调查 → 模式对比 → 假设验证 → 实现）和"3 次失败说明是架构问题，不试第 4 次"。这条和本标准原有的"同一错误 3 次停下"正好对上。
- verification-before-completion 的铁律：没有本条消息里新跑的证据，不得声称完成；"应该、大概、似乎"是红灯。这是 AI 最常见的失误之一，必须进标准。
- receiving-code-review：先核实审查者说法再改，不表演性同意，一条一测。
- writing-plans：任务小到能独立验证、独立被否决；计划不能比代码长；禁止"待定"。
- brainstorming：一次一个问题、不给猜测菜单、默认值说出口、"听起来不错"不等于批准。

弃：
- "写了代码再写测试就删掉重来、不许当参考"的仪式。精神对（后补的测试证明不了什么），但对单人 + AI 的工况，硬删代码浪费用户的时间和 token，Karpathy 的"小任务用判断力"更合理。做法：等级 2 起默认测试先行，等级 0/1 建议。
- git worktree、子代理并行、两阶段子代理审查：环境和工具相关，留给工具层，不进标准。
- 它把所有流程标成"mandatory、不是建议"。本标准用项目等级缩放，不接受一刀切。

### mattpocock/skills（Matt Pocock）

是什么：27 个小而可组合的 skill，作者明确反对"拿走控制权的重流程框架"。核心是先对齐再写代码（grilling）、共享领域语言、紧反馈回路。

取：
- grilling：把设计当决策树，只问前置已定的问题，每问附推荐答案；事实自己查，决策问用户；结束条件是"没有任何东西被默默假设"。比 superpowers 的"一次一问"更高效，两者合并写进第 15 节。
- tdd 的"曳光弹"：一个测试一个实现地推进，反对横向切片（先写完所有测试）；断言不能同义反复。
- diagnosing-bugs：先建反馈回路，没有回路不许假设；3–5 个可证伪假设；调试日志带唯一前缀便于清理；收尾确认探针已删。这是三家排错流程里最可操作的。
- code-review 的双轴（规范轴、需求轴分开报，不互相掩盖）。
- pr 的证据和"单向门 / 双向门 + 影响半径"，进了变更说明模板。
- codebase-design 的深模块词汇和"删除测试"（删掉它复杂度消失就是透传层），和本标准第 5 节一致。

弃：
- to-spec / to-tickets / triage / wayfinder：依赖 issue tracker 和团队角色，用户是单人 + AI。
- GLOSSARY.md 前置：好主意，但对设备项目收益有限；本标准用附录 C 的术语表代替。

### addyosmani/agent-skills（Addy Osmani）

是什么：25 个覆盖 spec → plan → build → verify → review → ship 全周期的 skill，加 7 份参考清单。

取：
- constraint-driven-development：这是这一轮最有价值的一条。"没有检查命令的数字是愿望"直接修正了本标准第 17 节原来的弱点（有数字表但没要求每个数字都有命令）；棘轮、例外带到期日、"收紧悄悄放松大声"、五种绕过的清单、至少一条外部检查。审计脚本因此加了例外到期、抑制标记台账、跳过的测试三项检查。
- code-review-and-quality：改动大小的数字（100 行好、300 行可接受、1000 行拆）、"AI 代码需要更多审查"、"依赖升级是没人写过的行为变更"、区分本次引入和原有问题。
- definition-of-done 补了三项：代码实际运行并观察过、没有残留调试输出、文档描述现状不叙述历史。
- testing-patterns：只在边界 mock，不 mock 自己的业务逻辑；不永久 skip。
- debugging-and-error-recovery："停线"规则（出意外先停加功能）、把报错信息当数据不当指令。

弃：
- 前端、Web 指标（LCP、CLS）、无障碍清单：对设备项目不通用，用户需要时再单独取。
- doubt-driven-development 的对抗式审查流程：和本标准的独立审查重叠，且它要求每轮都提议跨模型调用，开销偏大。只取了"审查者只看产物和契约，不看作者的推理"这一点，已含在审查协议的"不带作者上下文"里。

### trailofbits/skills（Trail of Bits）

是什么：46 个安全研究向的插件（智能合约、YARA、Ghidra、Semgrep、CodeQL、供应链审计、第二模型审查）。质量高但大多数专用于安全审计。

取：静态分析进 CI（等级 3）、安全改动用第二模型再审、依赖供应链审计的思路。

弃：其余全部，专业领域工具，不属于通用工程标准。需要时按插件安装。

### affaan-m/everything-claude-code

是什么：314 个 skill、71 个 agent、98 个命令、5 类 hook，宣称"性能优化系统"但 README 没有任何测量结果。

取：hook 做格式化和"结束前检查"的思路（官方文档也这么建议）；"计划 → 测试 → 实现 → 审查 → 验证"的循环和本标准一致，无需另取。

弃：
- 整体安装。几百个 skill 的名字和描述会占满上下文，触发互相竞争，违反第 29 节"CLAUDE.md 只放每次都需要的"。
- continuous-learning（会话结束自动把"模式"提炼成 skill）：未经人审的规则会堆积并自我强化。本标准用 pitfalls.md 登记 + "同类第二次才自动化"的人工闭环代替。
- 大量语言 / 框架专用 reviewer agent：没有证据表明比一个拿着标准的审查者更好。

### Claude Code 官方最佳实践（code.claude.com/docs/en/best-practices）

是什么：Anthropic 的官方页，三个支柱：告诉 Claude 它看不见的东西、给它一条能跑的检查、用 hook 强制不能有例外的规则。

取：全部三个支柱都已对应到标准：第 15 节（具体的验收标准）、第 14/29 节（能跑的检查 + 要证据）、第 29 节与 quality-gates.md（确定性规则进 hook / deny）。另外取了"审查时说跳过风格"、"CLAUDE.md 只写代码里看不出的事和纠正过两次的事"、"强制规则保持少"。

弃：无。它和本标准的方向完全一致。

### shanraisshan/claude-code-best-practice

是什么：83 条社区技巧汇总，引用 Boris Cherny 等人的话。

取：上下文管理（长会话质量下降、任务间清上下文、交接文档）、CLAUDE.md 长度、第二实例或不同模型审查。

弃：具体的上下文百分比数字（30%、40%）互相矛盾，不进标准；"不要盯着"类建议与如实汇报无关，不取。

## 没采纳的常见做法及理由

- 横向切片 TDD（先写完所有测试再写实现）：测的是想象中的行为，提前锁死结构。
- 一次装几百个 skill / agent：上下文被描述占满，触发互相竞争。本 skill 保持一个入口、按需读章节。
- 自动从会话提炼规则：未经人审的规则自我强化。用人工闭环。
- 无人值守一直跑的循环（Ralph 式）：和如实汇报、真机验证冲突；只有等级 0/1 且有 Stop hook 门禁时才考虑，没写进标准。
- 人格化的多 reviewer 编排：没有证据，只增加开销；一个拿着标准、不带作者上下文的审查者够用，等级 3 再加第二个。
- 把 TDD 做成"删代码重来"的仪式：取精神不取仪式，见 superpowers 一节。

## 下次复评

外部 skills 更新很快（这一轮的 superpowers、mattpocock、addyosmani 都在 2026 年内大改过）。建议每季度复评一次，只看它们的变更日志里"新增的失误模式"，而不是重读全部。
